# Translations

Two runtimes, two catalogs: PHP reads `.mo`, the block editor reads `.json`. The PHP side is routine;
the JS side has two traps that both fail **silently**, which is why translations disappear from the
editor and nobody can say when.

## Pipeline

```json
"translate":          "npm run translate:pot && npm run translate:update",
"translate:pot":      "wp i18n make-pot . ./resources/lang/sage.pot --include=\"theme.json,patterns,app,resources\"",
"translate:update":   "for file in ./resources/lang/*.po; do wp i18n update-po ./resources/lang/sage.pot $file; done",
"translate:compile":  "npm run translate:mo && npm run translate:js",
"translate:mo":       "wp i18n make-mo ./resources/lang ./resources/lang",
"translate:js":       "wp i18n make-json ./resources/lang --pretty-print --no-purge"
```

- `npm run translate` regenerates the source strings; `npm run translate:compile` builds the runtime
  artifacts. Two commands because you translate in between.
- **`--include` must list `theme.json`, `patterns`, `app` and `resources`.** Otherwise block
  `title`/`description` strings and pattern headers never reach the POT, and the inserter stays
  English no matter how complete the `.po` looks.
- `wp` must exist wherever these run. In a containerised setup that means inside the PHP container,
  not on the host.

## Sage does not load the PHP catalog for you

```php
add_action('after_setup_theme', function () {
    load_textdomain('sage', get_template_directory().'/resources/lang/'.determine_locale().'.mo');
});
```

In a mu-plugin, load it **before** anything registers labels — `register_post_type()` freezes them at
registration time:

```php
add_action('init', fn () => load_muplugin_textdomain('mytheme', 'lang'), -10);
```

## ⚠️ Trap 1 — `make-json` without `--no-purge` deletes your source strings

By default `wp i18n make-json` **removes the JS strings from the `.po`** after extracting them. On the
next run the `.po` no longer has them, the `.json` files regenerate empty, and the editor
translations vanish with no error. The only surviving copy would be whatever `.json` files happen to
be committed.

`--no-purge` is not an option, it is part of the command. Keep it in the npm script so nobody types
the command by hand.

## ⚠️ Trap 2 — a single editor bundle needs a hand-built merged catalog

`wp i18n make-json` emits one file **per source file**, named
`sage-<locale>-<md5-of-source-path>.json`. But the editor is a single webpack bundle
(`public/blocks/index.js`), so none of those hashes matches the registered handle's script path, and
WordPress finds nothing — again with no error.

Point the loader at one merged catalog instead:

```php
wp_set_script_translations('mytheme/blocks-editor', 'sage', get_theme_file_path('resources/lang'));

add_filter('load_script_translation_file', function ($file, $handle, $domain) {
    if ($handle === 'mytheme/blocks-editor' && $domain === 'sage') {
        $merged = get_theme_file_path('resources/lang/sage-'.determine_locale().'-editor.json');

        if (file_exists($merged)) {
            return $merged;
        }
    }

    return $file;
}, 10, 3);
```

The merged file is **built by hand** — a union of the per-source `.json` files:

```json
{
  "translation-revision-date": "…",
  "generator": "WP-CLI/2.7.1",
  "source": "public/blocks/index.js",
  "domain": "messages",
  "locale_data": {
    "messages": {
      "": { "domain": "messages", "lang": "it_IT", "plural-forms": "nplurals=2; plural=(n != 1);" },
      "Add question": ["Aggiungi domanda"]
    }
  }
}
```

Two details that are easy to get wrong:

- **Keep only entries with a real translation.** `make-json` emits untranslated strings as `[""]`, and
  an empty string is **not** a fallback to the source — it renders the label as an empty string. A
  panel with blank labels is the symptom.
- The domain inside `locale_data` is `messages` (the JS runtime's internal domain), while the domain
  passed to `wp_set_script_translations()` is the theme's. They differ on purpose.

Regenerate the merged file whenever editor strings change. If this becomes a chore, script the union —
but script it as *filter out `[""]`, then merge*, never as a plain concatenation.

## Language conventions

All code, comments, identifiers and commit messages in **English**, regardless of the client's
language. Only UI-facing strings are translatable, through `__()`/`_e()` with the theme's text domain
(`sage` by default in Sage) and the mu-plugin's own domain for its admin screens.

`block.json`'s `textdomain` must match the PHP domain, or `wp_set_script_translations()` has nothing to
attach to.

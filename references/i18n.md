# Translations

## The rule: an English codebase, translated at runtime

**On every project, everything in the code is English**: identifiers, comments, commit messages, and
**every string in the source** — `__()`/`_e()`/`esc_html__()` in PHP and Blade, `__()` in JS, block
`title`/`description`/`keywords` in `block.json`, labels of CPTs, taxonomies, meta panels and settings
pages. The client's language never appears in a source file, not even "temporarily".

What the visitor or the editor reads in Italian (or any other language) comes from a **translation
file**, which always exists:

- **Italian (`it_IT`) is created at kickoff and is mandatory** — for the theme and, separately, for the
  mu-plugin's own text domain.
- Other languages are added **on request**, one catalog per locale, from the same POT.
- A string is **done** only when it exists in English in the code **and** has its translation in every
  catalog the project ships. An untranslated entry is a bug, not a to-do: WordPress falls back to the
  English source, which on an Italian site looks like a half-finished job.

Not strings, and not translated through catalogs:

- **Content** — what editors type into blocks, posts, menus and options. It is stored in the site's
  language. Block copy that appears on insertion is seeded in the editor's language through a default
  block variation (`native-blocks.md` → *Placeholder copy*), never through `block.json` defaults.
- **Public URL slugs** of CPTs and taxonomies. The registration key stays English (`service`); the
  `rewrite.slug` is a content decision in the site's language (`servizi`), fixed, never wrapped in
  `_x()` — a slug that changes with the locale breaks every link. On multilingual sites, leave slugs to
  the multilingual plugin.

## Catalog layout

```
resources/lang/
├── sage.pot                    # generated — never edited by hand
├── it_IT.po  it_IT.mo          # mandatory
├── sage-it_IT-editor.json      # merged editor catalog (Trap 2 below)
└── de_DE.po  de_DE.mo  …       # only when requested
wp-content/mu-plugins/<plugin>/lang/
└── <domain>.pot  <domain>-it_IT.po  <domain>-it_IT.mo
```

The theme's PHP catalogs are named `<locale>.mo` because the loader below builds the path from
`determine_locale()`; the mu-plugin follows WordPress's `<domain>-<locale>.mo` convention for
`load_muplugin_textdomain()`.

At kickoff: create `sage.pot`, then `it_IT.po` from it (`msginit --no-translator -l it_IT -i
resources/lang/sage.pot -o resources/lang/it_IT.po`, or copy the POT and set the header), add the npm
scripts below, and the `load_textdomain()` hook. Ask whether any language besides Italian is needed.

**Adding a language later:** create `<locale>.po` from the current POT, translate every entry, run
`translate:compile`, build the merged editor JSON for that locale, and add the locale to the check
below.

## No untranslated string ships

Copy `assets/bin/translate-check` to `bin/translate-check`. It fails if the theme's `it_IT.po` is
missing, or if any catalog (theme or mu-plugin, any locale) has an untranslated, fuzzy or invalid
entry. Wire it into the theme's `package.json`:

```json
"translate:check": "../../../bin/translate-check"
```

(`msgfmt` comes with GNU gettext: `brew install gettext`.) Run it after `npm run translate` and before
every deploy; a string added without its Italian translation is caught here, not by the client.

Two runtimes, two catalogs: PHP reads `.mo`, the block editor reads `.json`. The PHP side is routine;
the JS side has two traps that both fail **silently**, which is why translations disappear from the
editor and nobody can say when.

## Pipeline

```json
"translate":          "npm run translate:pot && npm run translate:update",
"translate:pot":      "wp i18n make-pot . ./resources/lang/sage.pot --include=\"theme.json,patterns,app,resources\"",
"translate:update":   "for file in ./resources/lang/*.po; do wp i18n update-po ./resources/lang/sage.pot $file; done",
"translate:compile":  "npm run translate:mo && npm run translate:js",
"translate:mo":       "wp i18n make-mo ./resources/lang ./resources/lang",
"translate:js":       "wp i18n make-json ./resources/lang --pretty-print --no-purge"
```

- `npm run translate` regenerates the source strings; `npm run translate:compile` builds the runtime
  artifacts. Two commands because you translate in between.
- **`--include` must list `theme.json`, `patterns`, `app` and `resources`.** Otherwise block
  `title`/`description` strings and pattern headers never reach the POT, and the inserter stays
  English no matter how complete the `.po` looks.
- `wp` must exist wherever these run. In a containerised setup that means inside the PHP container,
  not on the host.

## Sage does not load the PHP catalog for you

```php
add_action('after_setup_theme', function () {
    load_textdomain('sage', get_template_directory().'/resources/lang/'.determine_locale().'.mo');
});
```

In a mu-plugin, load it **before** anything registers labels — `register_post_type()` freezes them at
registration time:

```php
add_action('init', fn () => load_muplugin_textdomain('mytheme', 'lang'), -10);
```

## ⚠️ Trap 1 — `make-json` without `--no-purge` deletes your source strings

By default `wp i18n make-json` **removes the JS strings from the `.po`** after extracting them. On the
next run the `.po` no longer has them, the `.json` files regenerate empty, and the editor
translations vanish with no error. The only surviving copy would be whatever `.json` files happen to
be committed.

`--no-purge` is not an option, it is part of the command. Keep it in the npm script so nobody types
the command by hand.

## ⚠️ Trap 2 — a single editor bundle needs a hand-built merged catalog

`wp i18n make-json` emits one file **per source file**, named
`sage-<locale>-<md5-of-source-path>.json`. But the editor is a single webpack bundle
(`public/blocks/index.js`), so none of those hashes matches the registered handle's script path, and
WordPress finds nothing — again with no error.

Point the loader at one merged catalog instead:

```php
wp_set_script_translations('mytheme/blocks-editor', 'sage', get_theme_file_path('resources/lang'));

add_filter('load_script_translation_file', function ($file, $handle, $domain) {
    if ($handle === 'mytheme/blocks-editor' && $domain === 'sage') {
        $merged = get_theme_file_path('resources/lang/sage-'.determine_locale().'-editor.json');

        if (file_exists($merged)) {
            return $merged;
        }
    }

    return $file;
}, 10, 3);
```

The merged file is **built by hand** — a union of the per-source `.json` files:

```json
{
  "translation-revision-date": "…",
  "generator": "WP-CLI/2.7.1",
  "source": "public/blocks/index.js",
  "domain": "messages",
  "locale_data": {
    "messages": {
      "": { "domain": "messages", "lang": "it_IT", "plural-forms": "nplurals=2; plural=(n != 1);" },
      "Add question": ["Aggiungi domanda"]
    }
  }
}
```

Two details that are easy to get wrong:

- **Keep only entries with a real translation.** `make-json` emits untranslated strings as `[""]`, and
  an empty string is **not** a fallback to the source — it renders the label as an empty string. A
  panel with blank labels is the symptom.
- The domain inside `locale_data` is `messages` (the JS runtime's internal domain), while the domain
  passed to `wp_set_script_translations()` is the theme's. They differ on purpose.

Regenerate the merged file whenever editor strings change. If this becomes a chore, script the union —
but script it as *filter out `[""]`, then merge*, never as a plain concatenation.

## Text domains

Every source string goes through a translation function with the right domain: the theme's (`sage` by
default in Sage) for the front end, blocks and editor UI; the mu-plugin's own domain for its admin
screens and labels. A string outside a translation function is untranslatable by construction — treat
it as a bug the same way as an Italian string in the source.

`block.json`'s `textdomain` must match the PHP domain, or `wp_set_script_translations()` has nothing to
attach to.

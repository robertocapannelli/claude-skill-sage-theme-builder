# Translations

## The rule: an English codebase, the main language in the catalog

**On every project, everything in the code is English**: identifiers, comments, commit messages, and
**every string in the source** — `__()`/`_x()`/`_n()`/`esc_html__()` in PHP and Blade, `__()` in the
editor JS, block `title`/`description`/`keywords` **and attribute defaults** in `block.json`, labels of
CPTs, taxonomies, meta panels and settings pages. The site's language never appears in a source
file, not even "temporarily".

The site's **main language** (asked at kickoff, `project-kickoff.md`) lives in a translation file:

- **Main language is not English** (say `de_DE`): the theme gets `resources/lang/de_DE.po/.mo`, each
  mu-plugin gets `<domain>-de_DE.po/.mo`, and the site locale is set (`WPLANG`, below). Without it,
  `<html lang>` and `og:locale` stay `en-US` on a non-English site.
- **Main language is English**: no catalog is required; the source is the text.
- Other languages are added **on request**, one catalog per locale, from the same POT.
- A string is **done** only when it exists in English in the code **and** has its translation in every
  catalog the project ships. An untranslated entry is a bug, not a to-do: WordPress falls back to the
  English source, which on a non-English site looks like a half-finished job.

### Converting strings that already exist

When a project has copy in its main language inside the code, **the text in the main language is the
authority**: the English is its translation, and the `msgstr` must be **identical, character for
character**, to the text that was there before. The site must not change by one letter — see
*Verify a mass conversion* below.

### Always the literal domain

```php
__('Add to cart', 'mytheme')      // extracted
__('Add to cart', TEXT_DOMAIN)    // NOT extracted
```

`wp i18n make-pot` only sees string literals: a constant or variable as the domain (or as the string)
is silently skipped, and the entry never reaches the POT. Write the domain as a literal every time.

## Not strings, and not translated through catalogs

- **Content** — whatever lives in the database stays in the site's language: posts, menus, terms,
  options, Contact Form 7 form templates, migration scripts. Titles used as a **lookup key** (the CF7
  form found by its title, a menu by name) stay exactly as they are: translating one breaks the lookup.
- **The builder credit** in the footer ("Crafted by …"): fixed copy, identical in every language,
  written literally and excluded from machine translation (`project-kickoff.md` → *Builder credit*).
- **Public URL slugs** of CPTs and taxonomies. The registration key stays English (`service`); the
  `rewrite.slug` is a content decision in the site's language (a translated word), fixed, never wrapped in
  `_x()` — a slug that changes with the locale breaks every link. On multilingual sites, leave slugs to
  the multilingual plugin.
- **Block copy typed by editors** is content. Copy a *new* block shows on insertion is seeded through a
  default variation (`native-blocks.md` → *Placeholder copy*); copy that lives in `block.json` defaults
  is covered by *Block attribute defaults* below.

## Set the site language

```bash
wp language core install de_DE        # download core translations
wp language core activate de_DE       # sets the WPLANG option
```

On staging and production the same two commands (or Settings → General → Site Language). Check the
**effective** locale with `get_locale()`, not the option — they can differ locally. Skip all of this
when the main language is English.

## Catalog layout

```
resources/lang/
├── sage.pot                    # generated — never edited by hand
├── block-defaults.php          # generated, NEVER loaded — feeds make-pot (see below)
└── de_DE.po  de_DE.mo          # main language, unless it is English
wp-content/mu-plugins/<plugin>/lang/
└── <domain>.pot  <domain>-de_DE.po  <domain>-de_DE.mo
```

Both runtimes read the `.mo`/PO data through PHP; there is **no `.json` catalog** (editor strings are
handed to `wp.i18n` from PHP, below). The theme's catalogs are named `<locale>.mo` because the loader
builds the path from `determine_locale()`; the mu-plugin uses `<domain>-<locale>.mo`.

At kickoff: create `sage.pot` (`bin/translate` needs a POT to exist), then the main-language PO from it
(`msginit --no-translator -l de_DE -i resources/lang/sage.pot -o resources/lang/de_DE.po`), the
mu-plugin's equivalent, the npm scripts below and the loaders. **Adding a language later:** `msginit`
from the current POT, translate every entry, `bin/translate compile`.

## Tooling: `bin/translate` and `bin/translate-check`

Copy `assets/bin/translate`, `assets/bin/translate-check` and `assets/bin/block-defaults-pot.mjs` to
`bin/`. Wire them into the theme's `package.json`:

```json
"translate":         "node ../../../bin/block-defaults-pot.mjs && ../../../bin/translate",
"translate:compile": "../../../bin/translate compile",
"translate:check":   "../../../bin/translate-check"
```

- `bin/translate` — one component per theme and per mu-plugin (each is a directory with a POT). It
  regenerates the POT with `wp i18n make-pot`, merges it into every PO with `msgmerge
  --no-fuzzy-matching` (a changed msgid becomes an **empty** entry to translate, never a guessed fuzzy
  one) and, with `compile`, builds the `.mo` files. Two steps because you translate in between.
- The theme's `make-pot` call includes `theme.json,patterns,app,resources`. **Without all four**, block
  `title`/`description` strings and pattern headers never reach the POT, and the inserter stays English
  no matter how complete the PO looks.
- `bin/translate-check` fails on an untranslated, fuzzy or invalid entry in **any** catalog, and on a
  missing catalog **for the site's main language**. It learns the language from `MAIN_LOCALE` /
  `--main-locale=` or `wp option get WPLANG`; English needs no catalog, so it never demands a catalog.
  Run it after `npm run translate` and before every deploy.
- `wp` must exist wherever these run: inside the PHP container for a containerised setup. `msgfmt`,
  `msgmerge` come with GNU gettext (`brew install gettext`).

## Loading the catalogs

The theme — Sage does not load the PHP catalog for you:

```php
add_action('after_setup_theme', function () {
    load_textdomain('sage', get_template_directory().'/resources/lang/'.determine_locale().'.mo');
});
```

### ⚠️ Trap — a mu-plugin catalog is not loaded by `load_muplugin_textdomain()` (WP 6.7+)

Since WordPress 6.7, `load_muplugin_textdomain()` only **registers a path** for just-in-time loading,
and that never runs if the domain is already loaded — for example by the theme. The strings stay
English with no error. Load the file explicitly, **before** anything registers labels
(`register_post_type()` freezes them at registration time):

```php
add_action('init', function () {
    $domain = 'mytheme';
    load_textdomain($domain, __DIR__.'/lang/'.$domain.'-'.determine_locale().'.mo');
}, -100);
```

A missing file (English site) just returns `false`; nothing to guard.

## Editor strings: hand the catalog to `wp.i18n` from PHP

The editor is one Vite/webpack bundle, so there is no script handle for `wp_set_script_translations()` to
match — and `wp i18n make-json` would need per-source hashed files, a merged file and a rule against
`[""]` entries. Skip all of it: pass the PHP catalog of each domain straight to the JS runtime.

```php
add_action('enqueue_block_editor_assets', function () {
    foreach (['sage', 'mytheme'] as $domain) {
        $translations = get_translations_for_domain($domain);
        $data = ['' => [
            'domain'       => 'messages',
            'lang'         => determine_locale(),
            'plural-forms' => $translations->headers['Plural-Forms'] ?? 'nplurals=2; plural=(n != 1);',
        ]];

        foreach ($translations->entries as $entry) {
            // An empty string is NOT a fallback to the source: it renders a blank label. Drop it.
            $strings = array_values($entry->translations);
            if ($strings === [] || in_array('', $strings, true)) {
                continue;
            }
            $key = ($entry->context !== null ? $entry->context."\x04" : '').$entry->singular;
            $data[$key] = $strings;
        }

        if (count($data) > 1) {
            wp_add_inline_script(
                'wp-i18n',
                'wp.i18n.setLocaleData('.wp_json_encode($data).', '.wp_json_encode($domain).');',
                'after'
            );
        }
    }
});
```

- It sends the **whole domain**, not only the editor strings: simple and correct, at the cost of a few
  tens of KB in the editor. The front end is untouched.
- **Keep only entries with a real translation.** `[""]` is not a fallback; it blanks the label.
- Nothing to rebuild when a string changes: it reads the live `.mo`. Remove any old
  `load_script_translation_file` filter, `*-editor.json` and `translate:js` script.
- On an English site `get_translations_for_domain()` has no entries and nothing is emitted.

## Block attribute defaults

Defaults that carry visible copy can stay in `block.json` **in English** and be translated at runtime
by exact match of the string. This keeps the rule "every source string is English" without moving
copy out of `block.json`, and matters most on an existing site, where pages inherit the defaults
(`content-migrations.md`). A brand-new block can still start with `""` defaults and a default
variation (`native-blocks.md`); pick one approach per block.

**Server** — a `block_type_metadata` filter translates every string inside the `default`s, recursively:

```php
// app/setup.php — must be registered before blocks register on `init`
add_filter('block_type_metadata', function (array $metadata): array {
    if (($metadata['textdomain'] ?? null) !== 'sage') {
        return $metadata;
    }

    $translate = function ($value) use (&$translate) {
        if (is_string($value)) {
            return $value === '' ? $value : __($value, 'sage'); // phpcs:ignore WordPress.WP.I18n
        }

        return is_array($value) ? array_map($translate, $value) : $value;
    };

    foreach ($metadata['attributes'] ?? [] as $name => $attribute) {
        if (array_key_exists('default', $attribute)) {
            $metadata['attributes'][$name]['default'] = $translate($attribute['default']);
        }
    }

    return $metadata;
});
```

**Editor** — `registerBlockType(name, { ...metadata })` takes the `block.json` as imported, in English,
including `title`, `description` and `keywords`. One helper, used by every block's `index.js`
(`native-blocks.md`), translates all of it:

```js
// resources/js/blocks/_i18n.js
import { __, _x } from '@wordpress/i18n';

const DOMAIN = 'sage';

const translate = (value) => {
    if (typeof value === 'string') return value === '' ? value : __(value, DOMAIN);
    if (Array.isArray(value)) return value.map(translate);
    return value;
};

// Contexts match what `wp i18n make-pot` assigns to block.json strings.
export function localizeMetadata(metadata) {
    const attributes = Object.fromEntries(
        Object.entries(metadata.attributes ?? {}).map(([name, attribute]) => [
            name,
            'default' in attribute ? { ...attribute, default: translate(attribute.default) } : attribute,
        ])
    );

    return {
        ...metadata,
        title: _x(metadata.title, 'block title', DOMAIN),
        description: metadata.description ? _x(metadata.description, 'block description', DOMAIN) : metadata.description,
        keywords: (metadata.keywords ?? []).map((keyword) => _x(keyword, 'block keyword', DOMAIN)),
        attributes,
    };
}
```

**POT** — make-pot extracts a block's `title`/`description`/`keywords` but not attribute defaults, and
it cannot follow `__($value, …)`. `bin/block-defaults-pot.mjs` writes `resources/lang/block-defaults.php`,
a PHP file **never loaded**, with one literal `__('…', 'sage')` per default string, so make-pot picks
them up. It skips empty strings, defaults of `enum` attributes and slug-like values (`left`, `dark`),
so visible one-word copy starts with a capital. `npm run translate` runs it first.

⚠️ **Changing the English of a default without its translation changes every page that inherits it**
(the exact-match lookup now misses, and the site shows English). Edit the English and the `msgid` in
every PO together, and treat it like any default change (`content-migrations.md`).

## Verify a mass conversion

Converting existing strings is a refactor whose only acceptable result is *no visible change*. Before
touching anything, and again after, snapshot **every public URL** (sitemap + templates + archives +
a page per block) and compare:

- the visible text, and the attributes `alt`, `aria-label`, `placeholder`, `title`, `value`;
- the JSON-LD graph;
- take **two consecutive "after" snapshots** and diff them against each other: whatever differs is
  random content (rotations, nonces, "related" lists) — ignore it in the before/after comparison.

The only differences allowed are strings that were **already English** before. Anything else is a
`msgstr` that is not identical to the original, a missing entry, or a string that fell outside a
translation function. Do this before reporting the conversion as done.

### Splitting the work between agents

Each agent writes its pairs to its own JSONL, one object per line:
`{"file":"…","msgid":"English","msgstr":"original main-language text","context":null}`. Merge them with
a step that **reports conflicts** — the same `msgid` with two different `msgstr` — instead of picking
one:

```bash
jq -s 'group_by([.context, .msgid])[] | select(([.[].msgstr] | unique | length) > 1)' pairs-*.jsonl
```

A conflict means one English word covers two meanings: resolve it with `_x('Order', 'purchase', …)` vs
`_x('Order', 'sequence', …)`, never by letting one win.

## Text domains

Every source string goes through a translation function with the right domain, written as a literal:
the theme's (`sage` by default in Sage) for the front end, blocks and editor UI; the mu-plugin's own
domain for its admin screens and labels. A string outside a translation function is untranslatable by
construction — treat it as a bug, the same as a main-language string in the source.

`block.json`'s `textdomain` must match the PHP domain, or core cannot translate the block's
`title`/`description` and the `block_type_metadata` filter above skips it.
